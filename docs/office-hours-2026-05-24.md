## Problem Statement

作为 DevOps/CICD 微服务软件架构师 + AI/agent 架构师,日常工作里架构产物(wiki / ADR / 影响面 / 设计文档)的**质量"看心情"、review 时漏关键点**,且每次接手新系统或评估新需求都重复手动劳动。**要建一套面向高级架构师的 evidence-driven workflow skill suite,以「架构交付件」为中心**,而不是又一个 coding agent。

目标:**降低日常架构工作噪音 + 提高决策与输出效率**。后续开源。

---

## What Makes This Cool(差异化 / 价值点)

1. **以交付件为中心的差异化定位** — 市场上 wshobson/agents(35k⭐)、VoltAgent(20k⭐)、aider、Cline 等大合集都是 generation 助手(role agent / point skill),**没有人把架构师的完整闭环(理解→探索→决策→建模→评审→沟通)做成 workflow**。
2. **5 + 1 YAML 证据契约** — subagent 与主上下文之间的 schema 化契约层,把"证据驱动"做进执行机制(不仅是 PPT 口号)。
3. **双层交付模型** — 智能体证据包(事实源)+ 人类 Wiki(导航层)分离,wiki 6 页 + 5 yaml + 1 org KB 类。
4. **反合理化清单 + goal-driven 验收 loop** — 自动回炉到达标才停。
5. **brownfield 主战场** — `arch-analyze` 现状测绘是核心,不是 greenfield-leaning。
6. **企业知识库 first-class** — moat 的人机协作接口具体落地。
7. **PRD 不清晰 hard gate** — frame 检测 ambiguity 强制产 PM 问题清单暂停 workflow,防止"在错误前提上做设计"。
8. **架构-as-code 边界明确** — 只产描述类,不产 IaC / DDL / pipeline 模板 / 骨架 / 业务代码,与 coding agent 一刀切开。

## Diagnostic(Office Hours Q&A 诊断)

### Q1 — Demand Reality: **A 强信号**

真实做过这类活,痛到套件能真省时间(不是 build-and-hope)。

### Q2 — Status Quo: **D 强信号**

现状混合手法(读代码 + Claude/GPT 对话 + IDE 调用链 + 脑内建模),**交付物质量看心情,review 漏关键点**——这正是套件的硬规则 + 验收 loop + 反合理化清单**直接对症**的点。

### Q3 — First 5 Users: **A 强信号**(第二轮 push 后给出)

第一轮答「所有希望提高决策效率的架构师」(category-level,典型 founder pitch 失败模式),第二轮 push 后,**能立刻 IM 给社区里 5 个具体人,大概率愿意装**。OSS 启动有 lighthouse customer。

### Q6 — Future-Fit(Moat): **A+B 复合**

- **A: Governance 随 LLM 加宝** — 证据可追溯 + append-only ADR + 反合理化门禁,LLM 越强(越"能乱产"),governance 层越必需。
- **B: 企业隐性约束 + 架构师决策标准** — 是人机协作接口,LLM 一辈子看不到企业内部的 banned patterns / 合规红线 / 网络边界。
- **复合 thesis**:**moat = (governance 随 LLM 能力提升而加宝)× (企业隐性约束 / 架构师决策标准是人机协作接口,LLM 无法独占)**。竞品(generation 助手)说不出这个。

### Q7 — Scope Gap: **A+B 都缺**

- **A. 企业知识库 first-class**(banned patterns / 合规红线 / 网络边界 / 命名规范 / 技术雷达)— 当前散在 `arch-library/`,不是一等公民
- **B. Architecture fitness function**(ADR fitness_spec + review --mode=fitness)— 当前没有可执行检查机制

## Constraints

- **只产描述类交付件**,不产可执行/可消费(IaC / DDL / pipeline / 骨架 / src 业务代码)
- **skill 总数 = 9**(含 `arch-radar` 按需)。**MVP 必跑 = 8**(不含 arch-radar)。当前活跃 user-facing skill(arch-onboard/design/audit/brief) 是其中第 1 个 = 编排器型 skill,不是单独"workflow 层"。
- **主上下文洁净**:heavy skill(analyze / judge / radar / review code 模式)**必须 subagent 隔离**
- 默认产物目录 **`arch/{project}/`**
- **5 类 project-scoped yaml + 1 类 org-scoped(含 5 个 yaml)** 是 schema 化契约层
- ni-skill 作为**第 3 track**(`skills/`),前缀 **`arch-*`**(无 ni- 前缀,与 harness track 的 `agent-legible` 同款)

## Glossary(给冷起步的工程师)

| 术语 | 含义 |
|---|---|
| `architecture_profile` | `arch-frame` 输出的字段:LLM 从代码+描述识别出的架构风格、主要关切、推荐加载的 references、推荐插入的 phase |
| `fitness_spec` | (v1.1)ADR 上的 optional 字段,把决策约束转译成可执行检查规格(grep / 文件路径 / AST 检测) |
| `fireworks-tech-graph` | 外部 Claude Code skill(7k⭐,github.com/yizhiyanhua-ai/fireworks-tech-graph),把自然语言描述渲染成 SVG/PNG 技术图,7 styles。`arch-diagram` 可选后端,不装则降级 Mermaid |
| `反合理化清单` | 当前活跃 user-facing skill(arch-onboard/design/audit/brief) 内置的硬规则集,封住 LLM 常见捷径(「先出报告证据后补」「这个仓看起来不重要」等),违反则拒绝继续 |
| `internal/phases/` | 预定义的 workflow phase 库,LLM 根据 `architecture_profile` 从库中挑选要插入的阶段(如 `eval-design` 给 AI 域),不让 LLM 现编 phase |
| `预算预告` | workflow 在执行 heavy phase(subagent 启动)前显式告诉用户:**预计 token 数 + 预计耗时 + 并行 subagent 数 + 涉及仓**。用户回车继续 / 输入缩小范围 / abort |
| `integrity check` | workflow 启动时检查 `arch/{project}/` 的文件完整性(state.yaml / evidence / wiki / diagrams 是否存在且通过 schema) |
| `prereq check` | workflow 启动时检查必要的前置产物是否就绪(audit 需要 baseline → 没就先 onboard) |
| `baseline` | `arch-analyze --depth=manifest` 产出的现状证据(仓库清单 + 依赖图谱),其它 mode/skill 都基于它工作 |
| `hard gate` | workflow 的强制门禁,不满足条件**禁止**进入下一 phase。例:PRD 检测出 ≥3 个未答问题时,frame 必须暂停产 `PM问题清单.md` |
| `mode` | 当前活跃 user-facing skill(arch-onboard/design/audit/brief) 的运行模式(`onboard` / `audit` / `design` / `brief`),每个 mode 对应一个状态机 pipeline |

## Premises(必须成立的前提,验证 v1.0 是否走得通)

1. **Premise 1**: v1.0 发布后 30 天内能拉到 5 个 first user 真用并给反馈——否则 OSS 模式崩,只剩 self-use,moat 第二层(企业约束/决策标准)永远验证不了。
2. **Premise 2**: Governance 价值随 LLM 能力变强而**加宝**——这一条要靠**实际数据**验证(跑半年后,看决策追溯次数 / 审计漂移命中次数 / ADR 复用率)。如果半年没人回看 ADR 也没人查证据,Q6 moat 论是脑补。
3. **Premise 3**: **Gap A(企业知识库 first-class)必须做进 v1.0**;Gap B(fitness function)v1.1 延后。**砍掉 Gap A 等于 moat 第二层是空话**,套件回退成"高级 prompt 集合"。

4. **Premise 4(新增,基于「Skill 文档债」论点)**: Skill 改动必须有 **Skill Regression Suite** 证明行为变化方向。否则 Skill 演进靠体感,不是工程化资产。
   - v1.0:占位结构 + case 模板(`internal/regression/_template/`),**手动**跑 ground truth(用户对照 case 看 trace 与输出)
   - v1.1:`arch-test` skill 自动跑全部 case + 回归报警
   - **未做 = 套件停留在"自然语言资产"阶段**,governance 论无法验证
   - 引用:[Skill 文档债 — 梯度不陡](https://mp.weixin.qq.com/s/46sZ3jbOapz_CP17gEbhXA)

## Approaches Considered

### Approach A1: 不新增 skill,扩 3 个现有 skill ✅ **Recommended (Accepted)**

- **Gap A(v1.0)**:新增**第 6 类 yaml 资产**——org-scoped 企业知识库
  - 位置:`~/.understand-arch/kb/`(用户级)或 `<org>/.arch-kb/`(团队级)
  - 内容:`banned-patterns.yaml` / `compliance-redlines.yaml` / `network-boundaries.yaml` / `naming-conventions.yaml` / `tech-radar.yaml`
  - **`arch-frame`** 启动时加载相关条目,写进 `项目总览.yaml.org_constraints`
  - **`arch-options`** 选方案时强制对照(违反 banned → 降级或拒绝)
  - **`arch-review`** 加 org-conformance 一致性检查
- **Gap B(v1.1 延后)**:**architecture-as-policy**
  - `arch-adr` 加 optional `fitness_spec` 字段
  - `arch-review --mode=fitness` 主动跑所有 ADR 的 fitness_spec
  - **延后理由**:需要 ADR 累积才有 enforce 对象;additive 字段,无破坏性

**净改动(v1.0)**:**skill 数 9 不变**,扩 `frame` / `options` / `review` 三个 SKILL.md,加 `~/.understand-arch/kb/` 目录约定。

### Approach A2(否决): 新增 `arch-knowledge` + `arch-fitness`

- skill 数 → 11,违反一路收敛"skill 少 = 降噪"原则
- `arch-knowledge` 90% 是 CRUD(读写 yaml),不值得独立 skill

### Approach A3(否决): 不补 A+B,9-skill v1.0 先发

- **违反 Premise 3**。首批用户拿到的就是"另一个 prompt 集合",moat 没建起来

---

## Recommended Approach: **A1 + Gap A in v1.0, Gap B in v1.1**

**Split 理由**:
- Gap A 是 **input 侧 data flow 改动**(frame 加载 org KB,options/review 对照),适合 v1.0 一次做对
- Gap B 是 **ADR 字段扩展 + 新 review mode**,additive,需要 ADR 累积才有意义,延后无破坏

### Behavior(关键不变量)

- **PRD 不清晰** → HARD GATE,产 `PM问题清单.md`,workflow 暂停在 `awaiting-pm-confirmation`,等用户/PM 答完(对话或编辑文件)才能继续
- **「审视当前项目/架构」** → 触发 audit mode
- **audit 触发但无 baseline** → 默认自动接 onboard,合并预算预告
- **integrity check** + **缺失自动恢复**(state.yaml / evidence / wiki / diagrams),append-only(ADR / design-docs / audits / briefs)不可重建
- **完整性 + prereq check** 在每次 workflow 启动前
- **反合理化清单**(防止"先出报告证据后补"等捷径)
- **Goal-driven 验收 loop**:
  - **Structural**(脚本/JSON Schema,秒级):字段完整、引用闭合、schema 通过
  - **Semantic**(LLM 评分 subagent,**强制使用 rubric checklist 而非自由判断**,**且 review subagent 与原产 subagent 必须不同**——避免同模型自证自评)。phase-end 跑结构 + workflow-end 跑语义
  - 失败自动 retry ≤ 2 次,**第 3 次仍不过 → 显式用户作裁判**(给四选项:retry with hints / manual fix / override skip / abort)。**不让 retry 进入空转**
- **HARD GATE 阈值(可计算,非主观)**:
  - PRD 不清晰:命中 ≥3 个具体未答问题(必填字段缺失 / 验收标准不可量化 / NFR 关键维度未表态 / non-goals 模糊 / 检测到歧义句 / 关键依赖未明,任一项算 1 个)
  - 必须产出 `PM问题清单.md` 作为 gate 的可验证证据
- **企业 KB 加载失败行为**:
  - `~/.understand-arch/kb/` 不存在 → degrade-with-warning,标 `org_constraints: not_configured`,继续 workflow(让首次用户能跑通)
  - 存在但某 yaml 文件 schema 不过 → **fail-loud**,告诉用户哪个文件哪行错,暂停 workflow
  - 部分 yaml 存在(如有 banned-patterns 没 compliance-redlines)→ 加载存在的,缺失的标 `not_loaded`,继续
- **AI/agent 域走 architecture_profile** 自动识别 + LLM 自选 references + LLM 自选 phase(eval-design 等)
- **第 6 类 yaml**:org KB 强制由 frame 加载,options/review 对照

1. **Self-use 验证**:v1.0 发布后 7 天内,你自己跑 onboard / design / audit 各至少 1 次,验收 loop 通过率 ≥ 80%

## Appendix A: 5 + 1 YAML Schema 草图(给冷起步工程师锚定契约)

完整 JSON Schema 放 `internal/schemas/`,这里给两个**最关键**的 sketch:

### `项目总览.yaml`(arch-frame 产出)

```yaml
project_name: string                 # kebab-case, ≤40 chars
generated_at: ISO-8601
generated_by: arch-frame
mode: onboard|audit|design|brief
```

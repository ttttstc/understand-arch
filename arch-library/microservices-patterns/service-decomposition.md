# Service Decomposition

> Scope: 服务拆分的原则、限界上下文、康威定律。`arch-frame` 在识别到微服务/多服务架构时,把这份加进 `arch-options` / `arch-review` 的上下文。

## 核心判断:该拆吗?

**默认答案:不拆。** 拆分前必须先回答:

1. **业务驱动是什么?** "微服务是潮流" 不是理由。可接受的驱动:
   - 不同业务能力的发布节奏差 ≥1 数量级(每周 vs 每季度)
   - 不同子系统的扩展曲线根本不同(读 100×写 / 突发流量 / 长尾任务)
   - 团队规模 ≥ 8 人 且每人的修改路径在单仓里**频繁冲突**
   - 合规边界(PCI / 敏感数据)要求物理隔离
2. **当前痛点能不能用模块化解决?** 90% 的"该拆微服务"其实是"该重构模块边界"。先在单体里画清楚 package / 子模块边界,半年后再判断。
3. **接受运维成本翻倍?** 服务数 = 1 → N 引入:服务发现 / 网络故障 / 分布式追踪 / 跨服务事务 / 部署编排。N≥5 时这些都成显性投入。

## 限界上下文(Bounded Context)

DDD 概念,**唯一**靠谱的拆分原则。不是按 CRUD 表拆,不是按技术层拆,按**领域语言边界**拆。

判定信号:
- 同一个名词在两处含义不同 → 是边界(典型:"订单" 在销售上下文 vs 履约上下文)
- 改 A 上下文的字段不会牵动 B 上下文的代码 → 是边界
- A 和 B 各自有独立的领域专家 → 是边界

反例(不该拆):
- "用户" 服务 + "权限" 服务 + "个人资料" 服务 — 全在同一个身份上下文,拆完每次新加字段三处改
- "订单创建" 服务 + "订单查询" 服务 — 同上下文不同操作,该是 CQRS,不是拆服务

## 康威定律的双向利用

> "组织设计的系统,最终镜像组织的沟通结构。"

正向用法:**先调组织,再拆服务**。如果两个团队不会经常协调,把它们的代码拆开。如果两个团队需要每天一起改一个东西,把代码合回去。

反向用法:**用拆分倒逼组织**。这个非常危险,只在已经决心做组织变革时用。否则就是制造长期跨团队耦合。

## 拆分阶梯(由轻到重)

1. **模块化单体**(modular monolith)— 单仓单部署,内部强边界;v1 默认起点
2. **共享库抽出**— 真正稳定的横切关切(eg. 日志格式、ID 生成)抽 lib
3. **第一刀切**— 拆出一个有强独立扩展需求的服务(典型:文件转码、推送)
4. **完整微服务**— 大部分领域上下文各成服务

**绝大多数项目卡在 1-2 之间是最优的**,不必往下走。

## 数据所有权

每个服务**独占**自己的数据(自己的 schema,理想情况自己的 DB)。

跨服务读 → 调 API 或订事件,**不直连别人的库**。直连库 = 表面拆开实际耦合死,改 schema 全连环动。

例外:历史包袱期允许 read-replica,但需要明确 deprecation 计划 + 加 R-NNN 风险条目。

## 服务间通信

| 场景 | 选择 |
|---|---|
| 同步查询 / 命令 | REST / gRPC |
| 通知 / 解耦 / 重试 | 事件总线 |
| 短周期工作流 | saga 编排(orchestration) |
| 长周期跨域事务 | saga 协同(choreography)— 但要小心调试地狱 |
| 大批量数据流 | 批 ETL,**不要**搞 100k 条消息 |

**禁止**:跨服务分布式 2PC 事务 — 现代系统几乎都该改成 saga 或最终一致。

## 常见反模式

- **分布式单体**:服务拆了但部署/发布必须同步 → 没收到拆分收益,只吃了拆分成本
- **微服务 × 共享数据库**:见上,数据所有权破了 = 假拆
- **粒度太细**:30 个微服务里 20 个是 "thin wrapper around a table" → 该合
- **共享 DTO 库**:跨服务共享请求/响应类型 → 每次改 DTO 全连环动 → 用 schema(protobuf / openapi)+ 各自生成
- **同步链 ≥3 跳**:A→B→C→D 同步调用 → 任何一跳挂全挂,且 latency 累加 → 拆 saga 或预聚合

## 重构方向(若已经拆错)

- 太多细服务 → **合并**回大服务,从测试覆盖率最高的开始合
- 共享 DB → 双写期 → 分库
- 同步链 → 引入事件 + 异步化(注意要把 SLA 改成最终一致)

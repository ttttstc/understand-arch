# Strangler Fig Pattern

> Scope: 通过在老系统外围逐步增长新系统、按业务能力切流,最终把老系统"绞杀"掉。`arch-frame` 在识别到 brownfield 大改造 / 单体拆服务 / 跨平台迁移时加载。

## 核心隐喻

Martin Fowler 借自然界的绞杀榕(strangler fig)— 寄生于宿主树外侧,逐渐包围、最终取代,**不需要砍倒宿主**。架构改造同理:不要 big-bang rewrite,而是在老系统旁建新系统,流量按能力逐步切。

## 为什么不直接 rewrite

Big-bang rewrite 的真实失败率:80%+(行业经验)。失败模式:
- 老系统的边界 case 没人记得,新系统漏实现 → 上线后翻车
- 项目周期 > 半年 → 业务需求变了,新系统目标移位
- 切换日"All-or-nothing" → 出问题不能回退,只能加班修
- 老系统继续在跑 → 双份维护 + 双向不一致

Strangler 把这些拆成可控小步,**每一步都能回退**。

## 实施步骤(canonical sequence)

### Step 1: 边界识别

找一个**业务能力子集**(不是技术层),它满足:
- 边界相对清晰(API / 库 / 模块)
- 老代码这一块改起来痛
- 业务能接受这块短期内被新旧两套服务

**反例**:不要先拆"DB 访问层"或"日志模块"— 那是技术切片,不是业务切片,绞不死任何东西。

### Step 2: 在外围建新实现

新建一个服务 / 模块,实现选定能力的完整闭环(自己的 DB / 自己的 API / 自己的部署)。**不依赖**老系统的内部状态。

### Step 3: 加流量路由(facade / proxy)

在老系统调用点之上加一层路由,默认走老,可按规则切到新:
- API gateway 加路由规则
- 应用层加 `if (feature_flag)` 分流
- DB 层加 dual-write / dual-read

路由层必须**双向可切**,这是 Strangler 的安全网。

### Step 4: 灰度切流

按用户 ID / 租户 / 流量 % 逐步切到新:
- 0.1% → 1% → 10% → 50% → 100%
- 每步停留足够长,看 SLI / 业务指标
- 任何指标异常立刻切回 0%

### Step 5: 老代码下线

当新路径 100% 健康跑了一段时间(典型 1-2 个月),才下线老代码。**不要急着删** — 旧代码留在 repo 里"标记为 deprecated"几个月,真出问题还能挖回来。

### Step 6: 重复下一个能力

回到 Step 1,选下一块。

## Anti-Corruption Layer(ACL)

新旧之间几乎必然有概念/数据模型差异。ACL 负责**翻译**,**保护新系统不被老的模型污染**:

```
new-svc ←(纯净的 new 模型)──┐
                              ACL
old-svc ←(老的 legacy 模型)──┘
```

ACL 是一次性投入,迁移完成后跟着老代码一起删。**不要**让 ACL 本身变成永久依赖。

## Dual-Write / Dual-Read

数据迁移期的 4 阶段:
1. **Single-write old, single-read old**(起点)
2. **Dual-write, single-read old**(新表准备好但还不信)
3. **Dual-write, dual-read with comparison**(对比报告,验证一致)
4. **Single-write new, single-read new**(切完)

每步停留时间足够长,**对比报告**是关键 — 任何字段不一致是必修 bug,不是"接受"。

## 常见反模式

- **没有路由层**:切流量靠手动改代码 + 发版 → 不可逆,失败回滚困难
- **新旧共享 DB**:新服务直接读写老 DB → 没拆,是"加了一层" → 改 schema 仍是大爆炸
- **ACL 永久化**:迁移做完不删 ACL → 留下永久翻译层 → 后续维护更难
- **太大的"第一块"**:第一刀切了 30% 的功能 → 实质 rewrite
- **切流量不看指标**:盲切 → 复制了 big-bang 失败模式,只是慢一点
- **新老都得维护新功能**:业务还在迭代,新功能要在两边都加 → 项目无终点

## 时间预期

Strangler 完整迁移的现实时间:**6-24 个月**,取决于:
- 多少业务能力要切
- 老系统耦合多深
- 团队多少人能投入
- 业务能容忍多少"切流量期"的轻微抖动

低于 6 个月通常是低估;超过 24 个月通常是没真投入。

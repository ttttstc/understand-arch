# Specs Review Rubric

## 1. 目标

本文件约束 `arch-review --mode=specs` 如何判断一份 baseline 是否真的“可审视”，而不是只看文件存在。

## 2. 完整性问题清单

### 系统组成

至少要能回答：

- 系统有哪些主要仓库
- 主要组件是什么
- 每个组件大致负责什么
- 哪些组件是核心链路上的关键节点

若不能回答，`baseline` 至少应是 `partial`，并形成 warning。

### 依赖与接口

至少要能回答：

- 谁调用谁
- 哪些接口是边界
- 哪些外部依赖最关键
- 哪些依赖最脆弱

如果只有组件清单，没有依赖关系，不能判 baseline 可用于深入审视。

### 数据与链路

至少要能回答：

- 关键数据模型有哪些
- 谁拥有这些数据
- 关键业务链路如何走
- 哪些链路最不能乱动

### 部署与运行

至少要能回答：

- 主要部署单元
- 关键运行约束
- 哪些配置会改变系统行为
- 回滚时最难的部分是什么

### 风险与技术债

至少要能回答：

- Top 风险是什么
- Top 技术债是什么
- 两者是否被分开
- 每条是否有 owner、缓解方向、影响范围

## 3. 典型 findings 触发条件

### error

- 关键组成缺失到无法判断系统边界
- 数据所有权完全不明
- freshness_status 与 evidence 明显冲突
- 风险台账完全不可用

### warning

- 某个 4+1 视图只有部分覆盖
- 关键组件无 owner
- 关键外部依赖无 fallback 描述
- 关键链路存在但步骤描述过粗

### info

- 可以再补更清晰的依赖图
- known unknowns 可进一步分级

## 4. freshness 与完整性的关系

- freshness 好，不代表 baseline 完整
- baseline 完整，也可能因为 commit 漂移而不可信
- review 结论必须同时评价“完整性”和“新鲜度”

## 5. 中文结论建议

### 可继续使用

```text
当前 specs 基本能支撑架构审视，暂时不需要重新扫描全仓。
```

### 建议 refresh

```text
当前 specs 仍有参考价值，但部分关键组成或风险信息可能已过期，建议刷新 baseline。
```

### 不可依赖

```text
当前 specs 不足以支撑可靠的架构判断，建议先 refresh 或做 drift audit。
```

# v1.1 Fitness Spec

> v1.0 ADRs do not accept `fitness_spec`. This file reserves the shape for v1.1 so current designs do not paint the project into a corner.

## v1.0 Rule

If a user asks to include executable fitness checks in v1.0:

- Do not add `fitness_spec` to ADR YAML.
- Mention it as future work in Consequences or Evidence if relevant.
- Keep ADR schema v1.0-compatible.

## Proposed v1.1 Shape

```yaml
fitness_spec:
  rule: "API calls from public traffic must enter through gateway."
  check_type: grep|ast|file_presence|dependency_graph|custom_script
  target:
    include:
      - "services/**"
    exclude:
      - "docs/**"
  check_pattern: "<pattern or query>"
  severity: error|warning
  remediation_hint: "Route partner ingress through gateway service."
```

## Check Types

| Type | Use |
|---|---|
| grep | simple text/path rules |
| ast | language-aware source checks |
| file_presence | required artifact/config presence |
| dependency_graph | architecture graph conformance |
| custom_script | last resort, explicit owner required |

## Future Review Mode

`arch-review --mode=fitness` will:

1. Load accepted ADRs.
2. Extract `fitness_spec`.
3. Run checks.
4. Report pass/fail/inconclusive.
5. Link findings back to ADR IDs.

## Design Constraint

Fitness specs must remain descriptive architecture checks, not production code generation. The suite may describe checks and run simple review-time validations, but it must not generate CI pipelines or deployment enforcement code.
